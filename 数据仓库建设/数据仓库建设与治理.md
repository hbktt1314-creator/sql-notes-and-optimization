# 数据仓库建设与治理

## 数据仓库为什么要分层

1. **隔离异常数据影响：**数仓中每一层的数据都经过分析处理，减少异常数据对其他层的影响。
2. **减少开发工作量：**每一层都可以作为平台层支撑上层的数据需求。当上层需求发生变化时，通常只需调整上层逻辑，减少对下层数据的改动。
3. **结构清晰：**数据分层后，繁杂的数据关系变得清晰，也更容易理清数据血缘。
4. **简化问题：**一项数据服务可能涉及多个原始数据表。在分层思路下，可以将数据服务需求拆解、划分为多个子问题。

## 数据仓库建设质量评价

### SQL复杂度

关注 ADS 层及看板 SQL 的复杂程度。逻辑应尽量清晰、可维护，避免将过多复杂处理堆积在最终查询中。

### 节点拓展性

评估数仓任务和数据模型能否适应业务增长、数据量变化及新需求。

### 每日异常ETL任务数量

ETL 任务是否正常决定数仓能否稳定提供服务。若 ETL 异常较多或重复出现，应检查任务调度和数据处理设计，例如：

- 对增量抽取数据量大的表，检查抽取策略是否合理。
- 每天只需要某个范围数据时，使用分区过滤，避免全量操作。
- 根据业务需求合理设置调度时间，避免任务集中运行。
- 对数据量非常大的表，可考虑拉链表、分区等方案；分区数较多时，可评估合并历史分区。
- 对经常变动的宽表，可评估竖表转宽表等建模方式。

### 每日新增数据量变化

稳定的数据仓库或数据中台，每日新增数据量通常在一定范围内波动。除业务特殊时间节点外，若数据量大幅变化，应检查是否存在数据异常。

### 查询速度

在资源有限的情况下，可考虑拉链表、分区设计和 SQL 优化（例如处理数据倾斜）来改善查询速度。

### 数据字典

数据字典与元数据相关，通常记录数仓中的业务字段、表数据量、表数量和数据分布等信息。通过查看数据字典，可以了解数据全貌，并在具备业务知识的情况下查缺补漏。

### 数据治理

数据治理主要面向异常数据。可与业务侧针对重要业务字段设定规则，以便提前发现脏数据和存疑数据。

## 数据倾斜

### 表现

Map Task 全部完成后，Reduce Task 长时间停留在 99% 左右。

### 原因

大量相同 Key 被分配到同一个 Reduce，导致该 Reduce 需要处理的数据过多，任务耗时显著增加。

常见原因包括：

1. Key 分布不均匀。
2. 业务逻辑或数据本身导致某些值高度集中，例如：
   - Join 的小表中 Key 分布集中。
   - 空值较多。
   - `GROUP BY` 的维度过少。
   - `DISTINCT` 操作可能导致单个 Reduce 处理大量数据。

### 处理思路

1. 在确认语义等价的前提下，评估使用 `GROUP BY` 改写 `DISTINCT`，并结合 Map 端聚合降低下游数据量。
2. 如果引擎支持并且执行计划验证有效，可将小表放在适当位置，以利用小表优先读取等优化；具体行为依 SQL 引擎而异。
3. 对足够小的表，可评估使用 Map Join，将小表加载到内存；需留意小表大小及执行引擎限制。
4. 单独处理倾斜 Key，例如对倾斜 Key 拆分处理，或为数据添加随机前缀进行分阶段聚合，最后合并结果。改写时应确保结果语义不变。

> 提示：倾斜优化策略需结合执行引擎、数据分布和执行计划验证；不要仅凭 Reduce 进度百分比判断根因。
